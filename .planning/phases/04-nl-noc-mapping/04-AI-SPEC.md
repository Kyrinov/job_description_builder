## 1. System Classification

**System Type:** RAG / Custom Retrieval Pipeline (Hybrid: retrieval + structured extraction)

**Description:**
The NL→NOC mapping system takes a plain-language work description from a Government of Canada HR advisor and returns a ranked list of NOC 2021 unit group candidates. It runs a custom three-stage pipeline: (1) FTS5 full-text search for keyword shortlisting across ~900 NOC profiles stored in SQLite, (2) sqlite-vec embedding rerank using nomic-embed-text embeddings via Ollama to surface semantically closest candidates, (3) a single configured local LLM call (via instructor) that produces a Pydantic-validated structured justification citing which specific NOC duty statements from the source records supported each match. The LLM sees only pre-screened candidates — never the full NOC corpus. Good output: a ranked list where the correct NOC group appears in position 1–3, every cited duty is verbatim from the database, and the justification is grounded in retrieved text.

**Critical Failure Modes:**
1. System returns an incorrect NOC code that propagates through the entire JD generation pipeline — producing a legally indefensible job description classified under the wrong occupational group and collective agreement
2. LLM generates justification text that fabricates or paraphrases duty statements not present in the retrieved NOC records — breaking the provenance requirement that every content element traces to an authoritative source
3. FTS5 shortlist misses the correct NOC entirely due to terminology mismatch — leaving the correct answer outside the rerank pool so it can never be surfaced regardless of LLM quality
4. Ranked list is returned without the specific NOC duty statements that supported each match — advisor cannot verify the match without source citations, defeating the auditability requirement

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Federal Government HR — Public Service Classification (Government of Canada, Department of National Defence)

**User Population:** DND HR classification advisors and accredited classification officers subdelegated by the Deputy Minister. These are subject matter experts in federal HR policy who know correct NOC mappings but use the tool to accelerate the initial shortlisting step and produce an auditable paper trail. They will immediately recognize and reject a wrong answer.

**Stakes Level:** Critical

**Output Consequence:** The confirmed NOC unit group is the entry point for the entire classification chain — NOC → Occupational Group → JES scoring → final Work Description. A wrong NOC at this step binds the position to the wrong collective agreement, wrong pay band, wrong staffing rights, and wrong JES standard. Errors at this step propagate silently through all downstream phases (5–8) and may only surface at grievance or TBS audit — at which point the JD must be redone from scratch and may trigger back-pay or reclassification proceedings.

### What Domain Experts Evaluate Against

| Dimension | Good (advisor accepts) | Bad (advisor flags) | Stakes | Source |
|-----------|----------------------|---------------------|--------|--------|
| Shortlist completeness | The correct NOC unit group appears in the top-3 ranked candidates | The correct NOC is absent from the returned shortlist — making the right answer unselectable regardless of the advisor's expertise | Critical | MAP-01/MAP-02 requirements; NOC automated coding research found 58.7% accuracy at 4-digit level without domain tuning (Turk et al. 2020, PMC7439137) — shortlist coverage must exceed model rank-1 accuracy |
| Duty citation verbatim fidelity | Every cited NOC duty statement is reproduced character-for-character from the database record for that unit group | Any cited duty that is paraphrased, summarised, reworded, or invented — even if plausible-sounding — constitutes a fabricated citation and breaks the audit trail | Critical | TBS Directive on Classification: every classification decision must be traceable to an authoritative source; ProvenanceTag requirement in DATA-01 |
| TEER level correctness | The returned candidate correctly identifies the TEER level (0–5) for the unit group, consistent with the NOC 2021 taxonomy | TEER level is missing, wrong, or inconsistent with the NOC code returned — a TEER error signals a structural retrieval failure, not a cosmetic one, because TEER determines training/education requirements | High | NOC 2021 TEER classification framework (ESDC/StatCan) |
| Ranking signal quality | The unit group whose duty statements most closely match the described work is ranked first or second; ranking reflects semantic fit, not keyword overlap alone | Top-ranked candidate shares surface vocabulary with the query (e.g., "analyst") but belongs to a different occupational domain — keyword collision producing a plausible-sounding wrong answer | High | Production RAG failure mode: embedding space does not encode specialist meanings; FTS5 keyword shortlist can surface false positives that dominate the rerank pool |
| Justification groundedness | The LLM's written justification for each candidate cites only duty statements that appear verbatim in the retrieved context window; no explanatory prose is generated beyond what the source records support | Justification contains connective reasoning or characterisation of the role that has no basis in any retrieved NOC record — advisor has no way to trace that claim to a source | High | TBS audit trail requirement; classification decisions must be substantiated by documentary evidence |

### Known Failure Modes in This Domain

1. **TEER collision** — Multiple NOC unit groups share similar duty vocabulary but sit at different TEER levels (e.g., TEER 2 vs. TEER 3 administrative roles). The embedding rerank surfaces the wrong TEER-level group because the semantic distance between duty statements is small. The advisor receives a confident-looking wrong answer. This is the federal HR equivalent of a correct-sounding but wrong NOC — it binds the position to the wrong JES standard.

2. **AS/EC vocabulary bleed** — Work descriptions for policy-adjacent positions contain terms ("policy", "analysis", "advice") that appear in both AS and EC NOC profiles. The retrieval pipeline surfaces both groups in the shortlist without surfacing the TEER/scope distinction. The advisor must manually apply the TBS internal-vs-public-facing test. If the system does not surface this ambiguity explicitly, the advisor may confirm the wrong group and trigger an OG misclassification at Phase 5. (This is the #1 pain point identified by Whitney Chalebois, senior classification advisor, DND — SME meeting 2026-05-28.)

3. **Level-shopping proxy query** — A manager who already has a target classification in mind (e.g., EC-5) writes a work description that mirrors the language of that NOC profile rather than describing actual work. The pipeline correctly surfaces the targeted NOC, but the match is driven by vocabulary coaching rather than genuine fit. The system has no signal that the query was reverse-engineered. Downstream: the JD is built on a misrepresented work description.

4. **FTS5 terminology gap** — The advisor describes work using internal DND terminology, acronym-heavy language, or military jargon that has no lexical overlap with the plain-language duty statements in the NOC corpus. FTS5 returns zero or irrelevant candidates; the embedding rerank has a degraded pool to work from. The correct NOC is never retrieved. This failure is invisible — the system returns a result, but it was never in contention for the right answer.

### Regulatory / Compliance Context

| Instrument | Relevance to This Phase |
|-----------|------------------------|
| TBS Directive on Classification (effective 2020-04-01) | Requires a signed, dated job evaluation rationale that substantiates the classification decision and traces to documentary evidence. A NOC match produced without cited verbatim source statements does not satisfy this requirement. |
| TBS Policy on People Management | Establishes the deputy head's accountability for ensuring classification decisions are made in accordance with job evaluation standards. Errors at the NOC mapping step that propagate to a wrong OG undermine this accountability chain. |
| Federal Public Sector Labour Relations Act | Classification decisions bind positions to collective agreements. A wrong NOC → wrong OG binding can constitute an unfair labour practice if it results in incorrect collective agreement application. Grievances arising from misclassification are adjudicated by the Federal Public Sector Labour Relations and Employment Board. |
| ESDC NOC 2021 Standard | The authoritative occupational taxonomy used for this phase. NOC 2021 Version 1.0 replaced NOC 2016; TEER replaced the prior skill level system. All retrieval and ranking must reference NOC 2021, not prior versions. |

## 2. Framework Decision

**Selected Framework:** Direct Ollama SDK + instructor (no AI orchestration framework)

**Version:** `ollama==0.6.1` (already in requirements.txt), `instructor==1.15.1` (already in requirements.txt)

**Rationale:**
The three-stage retrieval pipeline (FTS5 → sqlite-vec → LLM justification) is custom-built on the existing SQLite + sqlite-vec infrastructure already completed in Phases 2–3. Adding LlamaIndex or LangChain would introduce 15+ transitive dependencies for zero retrieval benefit — these frameworks add value when retrieval *needs* to be built, not when it already exists. The only new AI logic required is a single structured LLM call returning a Pydantic model with ranked candidates and cited duties — precisely what `instructor` already handles in this project (JES-01 uses the same pattern). Keeping the stack consistent with existing code also means every future developer can understand the pipeline without learning a framework.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex 0.10.x | Retrieval layer already custom-implemented; LlamaIndex's value is its retrieval abstractions, which are redundant here. Consider for Phase 5–6 if pipeline complexity grows. |
| LangChain 0.3.x | General-purpose wrapper overhead not warranted for a defined 3-stage pipeline with existing infrastructure; adds maintenance surface. |
| CrewAI | Multi-agent orchestration — wrong primitive for a retrieval-ranking pipeline. |

**Vendor Lock-In Accepted:** No — Ollama is model-agnostic; `instructor` works with any OpenAI-compatible API endpoint. Switching local models requires only changing the `model=` parameter.
