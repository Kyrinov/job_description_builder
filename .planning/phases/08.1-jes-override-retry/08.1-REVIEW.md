## Findings

### Info-1: `attempt-overload` advisory on retry route
- **File:** `app/api/jes_scoring.py:retry_jes_factor_route`
- **Note:** No rate limit on `/api/jes/retry/{wd_id}/{factor_name}`. A user could spam-click the Retry button and rack up LLM inference calls. The per-factor call is a single LLM completion (not the full 10-factor pipeline), so cost is bounded, but a future hardening pass could add a 1-call-per-second rate limit. **Out of scope for Phase 08.1** (defense-in-depth, not a security threat).
- **Disposition:** Accept — documented in CONTEXT.md as "the UI only shows Retry on failed factors" + "no bulk-retry endpoint exists" (T-08.1-04).

### Info-2: `regex-fallback` advisory on wizard_jes pre-validation
- **File:** `app/main.py:wizard_jes`
- **Note:** The regex `r"JES factor '(?P<name>[^']+)' is incomplete (level=(?P<level>[^,]+), points=(?P<points>[^)]+)) [—-]+ (?P<reason>.*)$"` is dependent on the exact error string format from `validate_export_readiness`. A future change to the error message could break the parsing. The fallback dict (`factor_name='(unknown factor)'`) ensures the error is still surfaced, but the user loses the deep-link to the right card.
- **Disposition:** Accept — fallback is in place. The error message format is now used in 3 places (service, regex, test), so a future change would surface quickly in CI.

## Code Quality Notes (non-findings)

- **Service-layer recovery functions mirror the existing `score_jes` pattern** (lines 195-214 of `score_jes` are referenced 1:1 in `retry_jes_factor`). Reuse is correct.
- **Order-preserving factor replacement:** `new_scores = list(wd.jes_scores); new_scores[factor_index] = new_score` — preserves the WD's `jes_scores` ordering, avoiding the "factor moved to the bottom" UX bug.
- **Sync vs async:** `retry_jes_factor` is async (LLM call), `override_jes_factor` is sync (no I/O latency to hide) — matches the existing pattern of other sync services in the codebase.
- **Jinja2 autoescape:** All `{{ }}` references are auto-escaped; no `| safe` filters. The `|urlencode` filter on `factor_name` in the URL path handles spaces and special chars.
- **CSS Layer 12** uses existing CSS custom properties with literal hex fallbacks — consistent with Layer 10/11 style. No new tokens added (Layer 13 can add `--color-success-text` / `--color-success-bg` if a broader refactor warrants it).

## Security

- All SQL queries are parameterized (verified by grep for parameterized binds in `app/services/jes_service.py` and `app/services/export_service.py`).
- `factor_name` flows through `|urlencode` in the URL — no URL injection.
- `rationale` (form field) is rendered via autoescaped `{{ }}` — no XSS.
- `level` / `points` are coerced to int (with form-level validation) — no type confusion.
- `wd_id` is a UUID path param, validated by parameterized SQL load — no SQL injection.
