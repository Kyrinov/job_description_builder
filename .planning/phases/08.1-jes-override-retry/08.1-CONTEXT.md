# Phase 08.1: Advisor override and per-factor retry for incomplete JES scoring — Context

**Gathered:** 2026-06-02
**Status:** Ready for planning
**Source:** User-identified gap during Phase 8 human-verify UAT (2026-06-02)

<domain>
## Phase Boundary

When the JES scoring pipeline (Phase 7) leaves factors incomplete — either because the model call failed after 3 retries (`level=-1` sentinel) or because the model returned a degree not in the factor's `point_values` dict (`points=None` silent-zero bug) — the Phase 8 export validator correctly blocks the export (D-01/D-02). But there is currently **no recovery path**: the user must re-run the entire 10-factor pipeline, which is slow, may fail again on different factors, and provides no per-factor visibility or control.

This phase adds two recovery mechanisms:

1. **Per-factor retry** — re-runs the LLM scoring call for a single failed factor
2. **Per-factor advisor override** — the advisor manually sets level + points + rationale, recorded with `advisor_adjusted=True` and `provenance.source_type=ADVISOR`

The export validator is updated to accept advisor-overridden factors; only unoverridden failures still block.

Out of scope: bulk re-scoring of all 10 factors (already exists via `POST /api/jes/score`), editing the factor's `point_values` JSON itself, undoing an override once set.

This phase ships AFTER Phase 8 human-verify UAT is approved, but is INSERTED into the roadmap now so it can be planned and ready to execute.
</domain>

<decisions>
## Implementation Decisions

### D-08.1-01 — Per-factor retry endpoint
- `POST /api/jes/retry/{wd_id}/{factor_name}` — re-runs the LLM scoring call for one factor
- Internally reuses the same scoring logic from `app/services/jes_service.py` (`_build_factor_user_prompt`, `JES_SCORING_SYSTEM_PROMPT`, `jes_instructor_client.chat.completions.create`, `_build_jes_factor_score`, `_make_error_score`)
- On success, the new score replaces the old one in `wd.jes_scores`, `wd.jes_total_points` is recomputed, the WD is saved (still in `stage='jes_scored'` — no stage advance)
- On failure, the old score is preserved (retry does not lose progress) and the route returns 422 with the failure reason
- Validation: WD must be in `stage='jes_scored'`, the factor must exist in the WD's `jes_scores`
- Response: HTMX partial (re-renders the single factor card) or JSON dict with the new score

### D-08.1-02 — Per-factor override endpoint
- `POST /api/jes/override/{wd_id}/{factor_name}` — advisor sets level + points + rationale manually
- Form fields: `level` (int), `points` (int, optional — auto-derived from factor's `point_values[degree]` if omitted, or `None` for "effort" factors with non-numeric scales), `rationale` (free text, min 10 chars)
- On submit: factor's `advisor_adjusted=True`, `advisor_adjusted_level=<level>`, `advisor_adjustment_rationale=<text>`, `provenance` is rebuilt as `ProvenanceTag(source_type="ADVISOR", source_id=f"{og_code}/{factor_name}", source_version="advisor manual override", retrieved_date=date.today(), modified_by_advisor=True)`
- The factor's `level` field is set to `advisor_adjusted_level`; `points` is set to the form value
- WD is saved; `jes_total_points` is recomputed
- Validation: WD must be in `stage='jes_scored'`; level must be a valid int ≥ 1; rationale must be ≥ 10 chars (advisor justification is the audit trail)

### D-08.1-03 — Validator accepts advisor-overridden factors
- `app/services/export_service.py:validate_export_readiness` updated:
  - For each `JESFactorScore` in `wd.jes_scores`:
    - If `advisor_adjusted=True`: skip the `level==-1` / `points is None` block (the override IS the resolution)
    - If `advisor_adjusted=False` and (`level==-1` or `points is None`): block as before, naming the factor
  - The empty-scores guard ("No JES factors scored") is preserved
- D-02 (silent-zero points is None) is replaced by a stricter rule for non-overridden factors: any non-overridden factor with `points is None` blocks; advisor-overridden factors with `points` set explicitly are accepted

### D-08.1-04 — Per-card Retry/Override buttons
- `templates/partials/jes_factor.html` — new partial that wraps a single factor card (extracted from `jes_scores.html`)
- For factors with `level==-1` or `points is None`:
  - **Retry** button: `hx-post="/api/jes/retry/{wd_id}/{factor_name}"`, `hx-target="#factor-{factor_name-slug}"`, `hx-swap="outerHTML"`, hx-indicator
  - **Override** button: toggles the override form open
- For successful factors: no buttons shown (no action needed)
- The existing `jes_scores.html` is updated to use the new partial in its loop

### D-08.1-05 — Override form partial
- `templates/partials/jes_override_form.html` — inline form for the override
- Fields: `level` (number input, 1–4), `points` (number input, optional), `rationale` (textarea, required, placeholder: "Justify the override — this is your audit trail")
- Submit: `hx-post="/api/jes/override/{wd_id}/{factor_name}"`, same target/swap as retry
- On success, the new card is rendered (with `advisor_adjusted=True` badge); on error (e.g., rationale too short), the form is re-rendered with the error inline

### D-08.1-06 — "Why is this blocked?" deep link
- Update `templates/partials/export_error.html` (created in `38eec77`): add a link "Why is this blocked?" pointing to `/wizard/jes?wd_id={wd_id}#failed-factors` so the user can jump to the JES page
- Update `templates/wizard/step_jes.html`: when loaded with a wd_id, pre-validate and add `id="failed-factors"` to the first failed factor card so the deep link scrolls to it
- This is a small UI touch to make the recovery flow discoverable

### D-08.1-07 — Provenance audit trail
- When an override is applied, the original LLM-produced score is NOT lost — it's moved to `advisor_adjustment_rationale` (which already captures the advisor's justification) and a new `ProvenanceTag` with `source_type="ADVISOR"` is created
- This keeps the audit trail clean: the DOCX export manifest will show both the original JES source (for reference) and the ADVISOR source for the override

### the agent's Discretion
- Exact CSS for the advisor-adjusted badge (use existing `.export-errors` / `.jes-factor-card--error` patterns; add a new `.jes-factor-card--advisor` modifier for the green/overridden style)
- Whether the retry endpoint supports a force-retry (re-running for a factor that already has a valid score is allowed but the UI only shows Retry on failed factors; force-retry is a future enhancement)
- How to handle the case where the factor's `point_values` JSON doesn't have a numeric scale (e.g., "Effort" factors) — allow `points=None` for advisor overrides on those factors; the validator will accept them since `advisor_adjusted=True`
</decisions>

<specifics>
## Specific Ideas

**Per-factor retry button** should be inline on the card (not a modal), so the user can re-run without losing their place in the scoring list. The button label should match the existing UI tone: "Retry" or "Rescore factor".

**Override form** should be collapsed by default and expand inline below the card. The form fields should mirror the LLM output: `level` (number), `points` (number, optional), `rationale` (textarea). On submit, the card is replaced with the overridden version showing a green "Advisor-adjusted" badge.

**Validator change** is minimal: add one conditional to skip the block check when `advisor_adjusted=True`. Keep the empty-scores guard.

**Audit trail** in the DOCX manifest: both the original LLM ProvenanceTag and the new ADVISOR ProvenanceTag are tracked. The `build_version_manifest` function in `export_service.py` already iterates all `provenance` fields, so this works automatically.

**No new requirement IDs**: this is a JES-01 extension (Phase 7) and EXP-01 extension (Phase 8) — the existing requirement coverage applies, no new IDs needed in REQUIREMENTS.md.
</specifics>

<deferred>
## Deferred Ideas

- **Bulk re-score of all 10 factors with progress UI** — already exists via `POST /api/jes/score`; the per-card buttons are additive
- **Undo an override** — once an advisor override is set, it cannot be undone via the UI; would require a "Reset to LLM score" endpoint (future)
- **Edit `point_values` JSON** — out of scope; that's a data integrity issue, not a UX issue
- **Persist override history** — the current model only stores the latest override; a full audit log (override created at, by, previous values) is a v2 feature
- **Multi-user override attribution** — single-user local app per REQUIREMENTS.md; no need for now
</deferred>
