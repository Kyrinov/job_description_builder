## v1 Requirements — All Complete

### Data Pipeline

- [x] **PIPE-01**: Developer can run an ingest pipeline that loads NOC 2021 unit group profiles, producing an FTS5 full-text index and a sqlite-vec embedding index (nomic-embed-text), with a content hash and version label recorded per source document
  — **Outcome:** Validated in Phase 2 (scripts/ingest_noc.py, 5-stage pipeline)

- [x] **PIPE-02**: Developer can run an ingest pipeline that processes collective agreement JSON files, extracting restriction/scope/exclusion clauses per OG using the configured local generation model, storing them as structured records in a queryable index keyed by OG code
  — **Outcome:** Validated in Phase 3 (scripts/ingest_ca.py)

- [x] **PIPE-03**: Developer can run an ingest pipeline that parses JES documents per OG, producing structured factor objects (og_code, factor_name, degree_descriptors, point_range) stored in SQLite
  — **Outcome:** Validated in Phase 3 (scripts/ingest_jes.py)

- [x] **PIPE-04**: Every source document ingested records a content hash and version label; every derived record stores the source document version hash it was derived from
  — **Outcome:** Validated in Phases 2–3 (content_hash + version_label on all ingested docs)

- [x] **PIPE-05**: On startup, the system asserts the embedding model name in the vector index metadata matches the currently configured model — the app refuses to serve queries on mismatch
  — **Outcome:** Validated in Phase 2 (assert_noc_index_model() in app/main.py lifespan)

### Core Data Model

- [x] **DATA-01**: The WorkDescription Pydantic model and SQLite schema are finalized before any service code is written — includes all TBS-required WD fields, a wd_audit_log table, and a ProvenanceTag type that every content element carries
  — **Outcome:** Validated in Phase 1 (app/models/work_description.py, app/db.py)

- [x] **DATA-02**: All runtime configuration is loaded from environment variables with startup validation — missing required variables cause an immediate startup failure with a descriptive error message
  — **Outcome:** Validated in Phase 1 (app/config.py with pydantic-settings)

- [x] **DATA-03**: The application pre-warms the Ollama connection and confirms the required models are available at startup, failing loudly if any model is missing
  — **Outcome:** Validated in Phase 1 (app/main.py lifespan + GET /health)

### NL→NOC Mapping

- [x] **MAP-01**: Advisor can describe work to be performed in natural language; the system runs a three-stage pipeline — FTS5 keyword shortlist → nomic-embed-text embedding rerank → configured local generation model structured justification — and returns ranked NOC unit group candidates
  — **Outcome:** Validated in Phase 4 (app/services/noc_mapping.py, 3-stage pipeline)

- [x] **MAP-02**: Each NOC candidate returned includes the NOC code, unit group title, TEER level, and the specific NOC duty statements from the source profile that best match the described work
  — **Outcome:** Validated in Phase 4 (NOCCandidate model with verbatim duty matches)

### OG Classification

- [x] **CLASS-01**: For the advisor-confirmed NOC match, the system presents the top 3 occupational group candidates side-by-side — each showing OG code, name, definition excerpt, relevant inclusions, and relevant exclusions, cited from TBS source documents
  — **Outcome:** Validated in Phase 5 (og_classifier.py + og_definitions table; 81 og_codes)

- [x] **CLASS-02**: Advisor confirms an occupational group and level before JD content generation proceeds — this is a hard workflow gate; no generation starts without explicit OG confirmation
  — **Outcome:** Validated in Phase 5 (422 gate on all Phase 6 endpoints without confirmed OG)

- [x] **CLASS-03**: For positions where the work description contains policy-related duties, the system surfaces the AS vs. EC distinction — with verbatim citations from data/directive_on_classification.txt
  — **Outcome:** Validated in Phase 5 (_fetch_directive_citation via FTS on policy_fts)

### JD Content Generation

- [x] **JD-01**: System drafts key duties/activities for the confirmed NOC and OG by selecting verbatim text from NOC profile statements stored in the database — the LLM ranks and selects from indexed records, it does not generate free-form duty text
  — **Outcome:** Validated in Phase 6 (jd_service.py — LLM selects from pre-indexed NOC records)

- [x] **JD-02**: Every duty and content element in the WD carries a structured ProvenanceTag: source type, NOC code, section name, statement text, and source document version hash
  — **Outcome:** Validated in Phase 6 (ProvenanceTag on every DraftDuty)

- [x] **JD-03**: Any content added by the advisor that has no source record is tagged "advisor-added / not from authoritative source" in the data model and rendered with a distinct visual indicator in the export
  — **Outcome:** Validated in Phase 6 (advisor_modified + ADVISOR source_type; DOCX renders marker)

- [x] **JD-04**: After duties are drafted, the system runs an orphan statement check — flagging any duty that contradicts the established authority for that OG; each flag cites the source rule by document and article
  — **Outcome:** Validated in Phase 6 (POST /check-orphan-statements endpoint)

### JES Scoring

- [x] **JES-01**: System generates a JES scoring sheet for the confirmed OG by making one configured local generation model call per JES factor — with the full factor descriptor and degree definitions injected fresh per call — returning a structured scoring object validated by Pydantic via instructor (max 3-attempt retry). Extended in Phase 8.1: per-factor retry and advisor override for failed factors.
  — **Outcome:** Validated in Phase 7 (jes_service.py) + Phase 8.1 (per-factor retry + override)

### CA Validation Infrastructure

- [x] **CA-01**: The data pipeline pre-extracts restriction, scope, and exclusion clauses from collective agreements per OG at ingest time, storing them as structured records indexed by OG code — foundation for active CA checking in v2
  — **Outcome:** Validated in Phase 3 (ca_clauses table, scripts/ingest_ca.py)

### Export

- [x] **EXP-01**: User can export the completed WD to DOCX (docxtpl) — every content element's source citation is rendered from its ProvenanceTag object; the export includes a version manifest of all source documents used
  — **Outcome:** Validated in Phase 8 (export_service.py; PDF deferred to v2 with 501)
  — **Adjusted:** PDF export returns 501 "not yet available" — DOCX is primary; PDF deferred to v2

### DND Integration

- [x] **DRF-01**: For DND positions, the system surfaces Departmental Results Framework program linkages connecting the position's duties to DRF expected results, sourced from the DRF dataset in data/
  — **Outcome:** Validated in Phase 9 (drf_service.py, inline panel on /wizard/export, DOCX Section 6)
